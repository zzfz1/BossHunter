# 本机 Codex Terra 自动评分

`scripts/codex_score.py` 通过本机 BossHunter Agent API 读取待评分岗位，用 `codex exec -m gpt-5.6-terra` 生成评分和招呼语草稿，再通过原有评估接口写回。

## 使用

先在服务器 Chrome 登录招聘平台。工作台发起采集时，关闭内置“采集后自动评分”，只采集岗位。后台服务会在采集结束且无其他任务运行时，自动处理待评分岗位；空队列不调用模型。内置“AI评分”和“全流程”仍使用独立 AI API，不应作为此桥接的入口。

```sh
systemctl --user status bosshunter-codex-score.service
journalctl --user -u bosshunter-codex-score.service -n 50 --no-pager
systemctl --user stop bosshunter-codex-score.service
systemctl --user start bosshunter-codex-score.service
```

服务每 60 秒检查一次，每轮最多处理 10 个岗位，串行调用。CLI 使用自己的登录状态，不读取或复制凭据，不需要在 BossHunter 填 API Key。模型推理在云端执行，使用 Codex 账户额度；用户已授权用于简历与岗位匹配。

## 写回与保护

- 使用上游五维评分提示和校验器；总分与封顶由程序计算。
- 模型不能指定岗位 ID、确认投递或调用发送接口。达到阈值的岗位写为 `ready`，招呼语仍待人工确认；其余写为 `filtered`。
- 上游预筛和任务互斥继续生效；不修改限频、每日上限和招聘平台风控。
- 模型在独立临时目录运行，禁用 shell、网页搜索和自由补丁工具，不加载用户 CLI 配置或项目指令。输入文档仅作为不可信数据。
- 原始提示与模型 stderr 不写入日志。缓存包含评分证据和草稿，位于 Git 忽略的 `data/codex-scoring/`，权限受限。
- 相同岗位、简历和配置复用缓存；POST 暂时失败时不重新消耗模型额度。状态已改变的岗位由 API 拒绝重复写回。
- 每份输入最多尝试模型三次，每次最多 240 秒；之后需人工排错。API 规则拒绝会标记 `blocked`，不自动改分迎合阈值。
- 简历或 JD 被接口截断、JD 缺失时不评分；先补全资料。

## 排错

`data/codex-scoring/status.json` 记录最近轮询状态；同目录散列名 JSON 记录尝试次数、缓存结果和写回状态。不要公开这些文件。

修复模型登录、网络或输入问题后，可停止服务，将需重试的对应散列 JSON 移至备份目录，再启动服务。不要修改岗位人工确认标记。

上游 pending 接口每次只返回最前面的 10 条且没有分页；如果这 10 条全部缺少 JD、被拦截或重试耗尽，后面的队列会等待。需在工作台处理这些岗位或补全资料后继续。

这是评分桥接，不是招聘采集计划任务；它不会自行开始采集，也不会自动投递、回复 HR 或发送简历。

## 求职者身份校验（2026-09-30）

评分使用评估员视角，招呼语明确切换为简历本人向招聘方自荐。桥接要求第一人称“我”，并在生成后及缓存写回前拒绝明显招聘方措辞；拒绝后沿用每份输入最多三次尝试。此规则是保守校验，不保证识别所有语义错误，草稿仍需人工审核。

缓存指纹包含提示词版本；旧版本记录保留但不再复用，不会重新评分已处理岗位。历史草稿需单独修复，不能仅靠更新提示词纠正。此次修复保持评分、岗位状态和人工发送确认边界。
